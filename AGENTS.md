# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a monorepo with a single application at `app/`. All commands below assume `cd app/` first; the repo root only holds `README.md` and `PRODUCT.md` (one-line stub: the product is a budgeting PWA for monthly budgets).

## Common commands (run from `app/`)

The package manager is **pnpm** (`pnpm-lock.yaml`, `packageManager` field). Node ≥ 20.19 is required (Prisma 7); `app/.nvmrc` pins 22.

```bash
pnpm dev             # vite dev server on port 3000
pnpm build           # vite production build → .output (Nitro, self-contained)
pnpm start           # run the built server: node .output/server/index.mjs
pnpm preview         # preview production build
pnpm test            # vitest run (one-shot, not watch)
pnpm lint            # biome lint
pnpm format          # biome format
pnpm check           # biome check (lint + format + organize imports)

# Prisma — all wrapped in `dotenv -e .env.local --` so DATABASE_URL is loaded
pnpm db:generate     # prisma generate (writes to src/generated/prisma)
pnpm db:push         # prisma db push
pnpm db:migrate      # prisma migrate dev
pnpm db:studio       # prisma studio
pnpm db:seed         # tsx prisma/seed.ts (configured via prisma.config.ts)
```

Run a single Vitest file/test: `pnpm exec vitest run path/to/file.test.ts -t "test name"`.

## Architecture

**Framework: TanStack Start** (SSR React on Vite). Scaffolded by `create-tanstack` (see `app/.cta.json`) with these add-ons baked in: **biome, prisma, db (@tanstack/react-db), tRPC, shadcn, tanstack-query, better-auth**. When extending, prefer these existing integrations over introducing parallel libraries.

**File-based routing** under `src/routes/`. `routeTree.gen.ts` is auto-generated by the TanStack router plugin (already excluded from Biome) — never edit it by hand. The root route (`__root.tsx`) is typed with a context of `{ queryClient, trpc }`, so every route loader/component can read `useRouteContext()` to access them without re-instantiating.

**Path aliases**: both `#/*` and `@/*` resolve to `src/*` (`tsconfig.json` + `package.json#imports`). The codebase currently uses `#/...` — match that.

**Data layer has three coexisting mechanisms** — pick deliberately:
1. **tRPC** (`src/integrations/trpc/`) — server-authoritative procedures, mounted at the file route `src/routes/api.trpc.$.tsx`. Uses `superjson` transformer on both ends. Define new procedures in `src/integrations/trpc/router.ts`; consume in components via `useTRPC()` from `src/integrations/trpc/react.ts` together with TanStack Query.
2. **TanStack Query** — set up in `src/integrations/tanstack-query/root-provider.tsx`; SSR-wired via `setupRouterSsrQueryIntegration` in `src/router.tsx`. The same QueryClient is shared with tRPC.
3. **@tanstack/react-db** (`src/db-collections/`) — client-side reactive collections (currently a `localOnlyCollectionOptions` example). Use for optimistic/local state, not as a substitute for tRPC server calls.

**Prisma** (`src/db.ts`) uses the new `prisma-client` generator with `@prisma/adapter-pg` (Postgres). The generated client is committed under `src/generated/prisma/` and imported as `./generated/prisma/client.js` — run `pnpm db:generate` after editing `prisma/schema.prisma`. A `globalThis.__prisma` singleton prevents connection storms during dev HMR.

**Auth: Better Auth** (`src/lib/auth.ts`, `src/lib/auth-client.ts`) with `tanstackStartCookies()`, mounted at `src/routes/api/auth/$.ts`. Email+password is enabled; the secret comes from `BETTER_AUTH_SECRET` in `.env.local` (generate via `npx -y @better-auth/cli secret`).

**Hosting: Nitro** (`nitro/vite` plugin in `vite.config.ts`, after `tanstackStart()`). Without it, `vite build` only emits a `fetch` handler with no listening server. With it, the build produces a self-contained `.output/server/index.mjs` (it bundles its own deps + serves the static client), run via `pnpm start`. `app/Dockerfile` is a two-stage build (pnpm install + build → copy `.output` into a bare `node:22-slim` runtime). The container needs `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` at runtime; build context is `app/`.

## Working on this app

- **Always run the app yourself** to verify a change actually works — `pnpm dev` from `app/` and exercise the affected flow in the browser. Type checks and unit tests don't count as verification for UI or end-to-end behaviour. If you genuinely can't run it (no browser available, env not set up), say so explicitly rather than claiming the change works.
- **Create your own test accounts when you need them.** Sign up via the running app, log in, and seed any needed state through the UI or `pnpm db:seed`. Don't ask the user for credentials.
- **UI components must come from shadcn/ui.** Add new ones with `pnpm dlx shadcn@latest add <component>` (registered in `components.json`, aliased to `#/components/ui`). Don't hand-roll buttons, inputs, dialogs, etc., and don't pull in another component library. Compose shadcn primitives; only write custom components when no shadcn equivalent exists.

## React & TanStack patterns

- **Follow the existing architecture.** Before adding a pattern, look at how the surrounding routes/components already do it (the three data mechanisms above, `useRouteContext()` for `queryClient`/`trpc`, the `_authed` layout) and match it. Don't introduce a parallel way of doing something that already has a home here.
- **SSR first.** Load data in the route `loader` (or `beforeLoad`) on the server and hand it to TanStack Query — prefetch/ensure the query in the loader and read it with the matching `useQuery` in the component, so the first paint is server-rendered and the client rehydrates the same cache. Reach for a client-only fetch only when the data genuinely can't be known at request time. Server-authoritative reads go through tRPC procedures, not ad-hoc `fetch`.
- **Avoid `useEffect`.** It's almost always the wrong tool here — there is usually a better solution:
  - Fetching/loading data → route loader + TanStack Query, not an effect.
  - Deriving a value from props/state → compute it during render (memoize with `useMemo` only if it's actually expensive); don't mirror it into state via an effect.
  - Responding to a user action → do it in the event handler, not in an effect that watches state.
  - Syncing with a truly external system (subscriptions, browser/DOM APIs, timers) → that's the legitimate `useEffect` case. If you write one, it should fall in this bucket and have a clear cleanup.
- **Watch local-state count.** If a component or page holds more than 2–3 `useState`s, treat it as a smell: the component is probably doing too much. Split it into smaller components, lift related fields into a single object/reducer, or move server state out into TanStack Query where it belongs.

## Conventions

- **Biome** is the only formatter/linter (no ESLint/Prettier). Config: tabs for indent, double quotes for JS strings, auto-organize-imports. `src/routeTree.gen.ts` and `src/styles.css` are intentionally excluded.
- **shadcn/ui** (new-york style, zinc base, lucide icons) — config in `components.json`, aliased to `#/components/ui`. Add components with the latest CLI: `pnpm dlx shadcn@latest add <component>` (per `app/.cursorrules`).
- **Tailwind v4** via `@tailwindcss/vite` — there is no `tailwind.config.*`; configuration lives in `src/styles.css`.
- TypeScript is strict with `noUnusedLocals`, `noUnusedParameters`, and `verbatimModuleSyntax` — keep `import type` separate from value imports.
